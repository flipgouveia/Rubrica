# Portability release checklist

ARCHITECTURE.md's own quality bar: *"an edit that only looks right inside Rubrica is a bug."*
CONTRACTS §9's portability gate requires two things of anything Rubrica writes: it re-opens in a
**fresh PDFium instance**, and it **parses with pdf-lib**. Both are automated and already run on
every commit (see [Automated coverage](#automated-coverage-already-in-place) below). This
document is the third leg the automation can't cover: a human opening the actual saved file in
**Acrobat Reader** and **a Chromium browser** and confirming it looks and behaves right — because
"parses without throwing" and "looks correct" are different bars, and only one of them is
checkable by a script.

## How to use this checklist

1. Generate one test artifact per row below by exercising the listed edit against the listed
   fixture (via the real app, `pnpm tauri dev`, or the e2e suite that produces these artifacts —
   see "Regenerating an artifact" below).
2. Open each artifact in **Acrobat Reader** and in **a Chromium-based browser** (Chrome or Edge's
   built-in PDF viewer). Check the box once you've looked at it and it's correct; if it isn't,
   don't check the box — file the specific problem instead of checking it anyway.
3. The two "automated" rows are already covered by the test suite (cited below) — they don't need
   a human to check them by hand, but they're listed here so this checklist is a complete picture
   of what "portability-verified" means for a release, not just the manual half of it.

A row with an empty checkbox below is genuinely unverified — this document ships as a template;
the checkboxes are for a human to fill in during the release pass, not something this task
generates screenshots or results for.

### Two known-fidelity items that need extra attention on rows 1 and 3

These aren't bugs — they're documented, accepted v1 tradeoffs (see `agents/reports/r5-report.md`
and `README.md`'s Known limitations) — but r5's report specifically flags them as needing a real
human look in a real desktop viewer before release, because they were never visually confirmed
outside the automated suite:

- **Row 1 (Annotated), shape sub-case**: the ellipse/line/arrow shapes are stored as PDF `Stamp`
  annotations (pdfium-render 0.9.3 has no API to create native Circle/Line annotations). The
  drawn appearance is standard, portable PDF and should render **visually identical** to what a
  native Circle/Line annotation would show in both viewers. Confirm this specifically — that the
  ellipse looks like an ellipse, the line looks like a line, and the arrow has a visible
  arrowhead — not just that the file opens.
- **Row 3 (Form-filled)**: confirm the "Not saved" badge on a non-checkbox field (try editing a
  text field) reads clearly in the live app before you even get to the saved-file check — this
  row's saved artifact should contain the checkbox changes correctly and should **not** contain
  any text/radio/combo/listbox edit you tried to make (since those never persist in v1; that's
  the point of this row existing separately from row 1's "everything works" cases).

## Regenerating an artifact

If a fixture in the table above needs to be regenerated by hand (rather than via the automated
e2e suite):

1. `pnpm tauri dev` to run the real app against the real engine (the mock engine in `pnpm dev`
   does not produce real files — it has no filesystem).
2. Open the listed source fixture from `fixtures/`.
3. Apply the listed edit(s) through the UI.
4. Save (or Save As, to avoid overwriting the fixture itself — recommended, so the checked-in
   fixture stays pristine for the next release).
5. Run the two automated checks against the saved file before opening it in a viewer by hand:
   ```bash
   pnpm verify:pdf path/to/saved.pdf
   ```
   (the fresh-PDFium-reopen half only runs as part of `cargo test`'s fixture suite today — see
   below — so a hand-produced file doesn't get that half automatically; the fixture corpus
   already does, which is why rows 7–8 point at the test suite rather than requiring a fresh
   manual run per release).

## Automated coverage (already in place)

Both automated rows above are real, running checks, not aspirational — they run on every `cargo
test` from `src-tauri/`, wired into the single sequential `engine_fixtures` test (PDFium is not
thread-safe in the vendored build — see `agents/reports/r2-report.md` — so the whole suite
runs as one test, sequentially, on purpose; this is expected, not a red flag).

- **Fresh-PDFium reopen**: `src-tauri/tests/engine_fixtures.rs`'s `assert_portable()` helper
  re-opens every saved file with a brand-new `Pdfium` handle (never the same handle that wrote
  the file) and asserts the expected page count — this is the "does PDFium itself, independently,
  agree this file is valid" half of the gate. Exercised by (non-exhaustive, one per artifact
  class above):
  - Row 1 (Annotated): `round_trips_every_achievable_kind`, `bbox_transform_updates_highlight_and_ink`,
    `undo_redo_round_trips_add_update_delete`, `deletes_and_updates_object_bearing_kinds_without_crashing`
    (`src-tauri/src/engine/annotations.rs`)
  - Row 2 (Page-edited): `reorders_pages_and_persists_the_new_order`, `rotates_pages_additively_and_persists`,
    `deletes_a_page_and_persists_remaining_content`, `inserts_a_blank_page_at_a_middle_index`,
    `inserts_a_page_range_from_another_fixture`, `reorder_preserves_annotations`,
    `page_ops_do_not_disturb_form_fields` (`src-tauri/src/engine/pages.rs`)
  - Row 3 (Form-filled): `reads_all_real_fields_from_form_pdf`, `sets_checkbox_and_persists_after_reopen`,
    `undo_redo_round_trips_a_field_value_change` (`src-tauri/src/engine/forms.rs`) — plus the
    non-crashing-rejection tests for the blocked kinds: `text_set_value_is_unsupported_not_a_crash`,
    `combo_set_value_is_unsupported_not_a_crash`, `radio_set_value_is_unsupported_despite_set_checked_reporting_ok`
  - Row 4 (Text-edited): `textedit_fixes_a_typo_without_font_substitution`,
    `textedit_edits_accented_pt_text_without_substitution`, `textedit_adds_a_text_box_and_an_image`,
    `textedit_object_delete_undoes_cleanly` (`src-tauri/tests/engine_fixtures.rs`)
  - Row 5 (Redacted): `redact_apply_leaves_no_trace_of_the_marked_text`
    (`src-tauri/tests/engine_fixtures.rs`) — this one goes further than a reopen: it decompresses
    the saved file's content streams and byte-searches to prove the redacted text is actually
    gone, not just visually covered
  - Row 6 (Mixed): `mixed_undo_redo_across_domains_stays_consistent`
    (`src-tauri/tests/engine_fixtures.rs`) interleaves commands across domains on one document;
    combined with the base fixture suite (`opens_text_pdf`, `opens_form_pdf_and_reports_has_form`,
    etc.) this is the closest existing automated analogue to row 6 — it does not currently chain
    literally every tool on one document in one save the way the manual row 6 artifact should
- **pdf-lib parse**: `scripts/verify-pdf.mjs` (`pnpm verify:pdf`) loads every fixture under
  `fixtures/` with `PDFDocument.load()` (encryption-aware, so `encrypted.pdf`/`corrupt.pdf` are
  correctly treated as expected-fail rather than a bug) — this is wired into CI
  (`pnpm bindings:check`'s sibling job) and can be pointed at any specific file via
  `pnpm verify:pdf path/to/file.pdf`.

Treat a clean run of both as **necessary, not sufficient** — that's the whole reason this
checklist's manual rows exist.
